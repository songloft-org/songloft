### CI-002: Read ffprobe packet hashes by field rather than slicing CSV lines

- Scope: video-copy verification in `TestHLSTranscodeRealFFmpeg`; baseline `af5a4b3873ba72e9918ddf661da87ae563448d36`.
- Failure evidence: on 2026-10-27, [Quality](https://github.com/songloft-org/songloft/actions/runs/40443632206) reported `video packet 39 changed` on Ubuntu / FFmpeg 6.1.1; the same old test passed ten times locally with FFmpeg 5.1.7. Its CSV parser kept everything from `SHA256:` to the line end, including subsequent fields. Real source and first-segment packet 39 have the same hash, but the source packet carries an MPEG-TS Stream ID while the final segment packet does not. The [ffprobe 6.1.1 source](https://github.com/FFmpeg/FFmpeg/blob/n6.1.1/fftools/ffprobe.c) prints `data_hash` before side data, making the old comparison depend on output layout.
- Rule and fix: compare compressed payloads through JSON `packets[].data_hash`, preserving packet order, nonempty output, SHA-256 field validation, and equality for every packet. Changes in CSV side metadata do not establish video reencoding. Do not skip the check, relax equality, or change production FFmpeg arguments.
- Done right: Linux amd64 / Go 1.26.0 / FFmpeg 5.1.7; `CGO_ENABLED=0 go test -tags dev,lite ./...`, matching vet, 59 script tests, formatting, and diff checks pass. An isolated Go overlay replacing video copy with libx264 reencoding makes the updated test fail on packet 0 as expected, retaining detection of actual data changes. Logs, tool versions, and version-comparison evidence are under `/tmp/songloft-ci-hls-20261027/`; Ubuntu 6.1.1 and post-push CI results must be checked against the delivered SHA.
- Not run: Safari, real IPTV sources, or physical-device playback. This only corrects test parsing and does not change server playback behavior.
- Seen 1× (2026-10-27). Status: test-compatibility lesson, separate from missing FFmpeg dependencies in CI-001.

### JSPLUG-001: Never advance resident-plugin async chains on a fixed polling period

- Scope: the background timer goroutine in `internal/jsplugin` and the async wake channel in `internal/jsruntime`, affecting every resident JS plugin. Failure instance: [songloft-org/songloft-plugin-miot#119](https://github.com/songloft-org/songloft-plugin-miot/issues/119).
- Failure evidence: on 2026-10-20, `runTimerProcessor` at baseline `7c9f9f341865514d8e606bdb90e01ac92e148208` used a fixed 500ms ticker, so every await continuation in a chain detached from `ExecuteJS` waited for the next tick. The reporter's [log](https://github.com/songloft-org/songloft-plugin-miot/issues/119#issuecomment-6281088024) shows `first_content_ms=1022` but `speech_dispatch_ms=9499`. In the same round, real `doHTTPRequest` round-trips on the Go side were 848/294/103/245ms, while the matching JS-side observations landed at 43.652/44.151/47.145/47.644 — all on the 500ms grid. The new `TestTimerProcessor_BackgroundChainIsNotPumpBound` fails against the old implementation isolated through an overlay, advancing only 4 of 10 hops in 2 seconds.
- Rule and fix: wake the pump goroutine immediately on `asyncSignal`, otherwise sleep until `GetNextTimerDeadline`, and fall back to 500ms only when neither applies. A `minWakeInterval = 10ms` floor keeps expired timers from spinning while a long request holds the VM lock. `executeInEnv` must `signalAsync` on return: timers a plugin registers during that call (`onInit` starting a background poll, `onHTTPRequest` deferring work with `setTimeout(fn, 0)`) are invisible to a pump goroutine that is already asleep. When investigating plugin latency, align host-side network timestamps with JS-side observations first; a difference that lands on a fixed grid is the pump period, not a slow upstream.
- Done right: Linux amd64 / Go 1.26.0 / Node 26.5.0, baseline `7c9f9f341865514d8e606bdb90e01ac92e148208` plus this uncommitted worktree. `make check` (gofmt, `go vet`, full Go tests) passes; the new regression passes at `-count=20` and at `-race -count=5`; restoring the fixed-ticker implementation through `go test -overlay` fails as expected (4 of 10 hops in 2 seconds). Logs: `/tmp/songloft-119-20261020/go-{before,after,race}.log`. Do not invoke the plugin while the regression waits: `InvokeHTTP` runs through `ExecuteJS`, whose own event loop would drain the chain on the pump goroutine's behalf and mask the regression. Bound elapsed time against a fraction of the old polling grid rather than the VM's actual speed, which is what keeps the assertion stable under `-race`.
- Not run: real speakers and long-running behavior; the end-to-end latency gain is inferred from logs and was not re-measured on a device. The plugin-side companion change is MIOT-011 in the submodule.
- Seen 1× (2026-10-20). Status: lesson; real-device confirmation and release verified separately.

### DOCKER-001: Select upgrades for the running architecture and reject execution failures before replacement
